# Plan: store tokens with fixed meanings

## Goal

Token columns get meanings we own, so stored rows never depend on upstream conventions again, and "tokens" means what OpenAI's `total_tokens` and Anthropic's usage mean: all input plus output. CLIProxyAPI has changed what `total_tokens` and `cached_tokens` mean over time, and we never stored or priced Claude cache writes.

## Schema

The `requests` table in `src/cliproxy_usage_collect/db.py` (authoritative) becomes, for its token columns:

```sql
  input_tokens          INTEGER NOT NULL,            -- all input: uncached + cache read + cache creation
  output_tokens         INTEGER NOT NULL,            -- all output, reasoning included
  reasoning_tokens      INTEGER NOT NULL,            -- part of output_tokens
  cache_read_tokens     INTEGER NOT NULL,            -- part of input_tokens (renamed from cached_tokens)
  cache_creation_tokens INTEGER NOT NULL DEFAULT 0,  -- part of input_tokens (new)
  total_tokens          INTEGER NOT NULL,            -- upstream's reported total; never read
```

`_INSERT` and every other `INSERT INTO requests` (tests included) name their columns, so column order does not matter (a migrated table has `cache_creation_tokens` last; a fresh one lists it as above). `RequestRecord` (`src/cliproxy_usage_collect/schemas.py`) follows the new names.

The layout is versioned with SQLite's `PRAGMA user_version`: 0 is the old `cached_tokens` layout (every existing DB), 1 is this one. `SCHEMA_VERSION = 1`, the `user_version` reader, the newer-DB error and the mismatch message live in a leaf module, `src/cliproxy_usage_collect/schema_version.py`, which `db.py`, `migration.py` and the server import (the server does not import `db.py`).

## Changes

1. **Collector parser** (`src/cliproxy_usage_collect/parser.py`) reads only the payload's `token_breakdown`: `input.total_tokens`, `input.cache_read_tokens`, `input.cache_write_tokens`, `output.total_tokens`, `output.reasoning_tokens` and `total_tokens` fill the columns above. A missing `token_breakdown` or a `schema_version` other than 2 is a `SchemaError`. A breakdown whose `quality` is not `complete` has no split: its token columns other than `total_tokens` are stored as 0 (the request still counts), and the collector's summary line reports how many such rows the batch had.
2. **Collector `open_db`:** a DB whose `user_version` is above `SCHEMA_VERSION` raises an error the CLI maps to exit 2 (config), before the queue is popped. A DB with no `requests` table gets the table, its indexes and version 1 in one transaction. A version-0 DB with a `requests` table is migrated. Both changes run under one write lock: take it, re-read the version (a newer one raises), and for a fresh DB the table presence, act or do nothing, commit. Any other SQLite error from `open_db` makes the collector exit 1.
3. **Migration**, in its own module `src/cliproxy_usage_collect/migration.py`, which `open_db` calls for version 0 (`user_version` replaces the `cached_tokens` column check, both before the backup and inside the transaction); nothing else in the code knows the old layout, and a follow-up commit deletes the module once the deployed DB is migrated. It writes a consistent copy to `<db>.pre-cache-columns` with `VACUUM INTO` (replacing an earlier file of that name), then in one `BEGIN IMMEDIATE` transaction re-checks that `user_version` is still 0 and, if so: sets it to 1, renames `cached_tokens` to `cache_read_tokens`, adds `cache_creation_tokens`, and rewrites rows whose model starts with `claude` (Anthropic accounting; every other model in the data already stores all input in `input_tokens`): cache creation = `MAX(0, total_tokens - input_tokens - output_tokens - cache_read_tokens)`, input = input + cache read + cache creation, both from the old values; every other row gets cache read = `MIN(cache_read_tokens, input_tokens)`, so no row has negative uncached input. Any migration failure, including a concurrent run holding the lock, leaves the DB unchanged and makes the collector exit 1 (transient) before the queue is popped, so cron retries.
4. **Server startup** (`run()` in `src/cliproxy_usage_server/main.py`, before uvicorn starts): when the DB file exists, it reads `user_version` through `open_ro`; if that differs from `SCHEMA_VERSION` (or cannot be read), the server exits non-zero with a message naming both versions and what to do (version below: run `cliproxy-usage-collect` once to migrate; above: upgrade the server). It does not check again after startup.
5. **Per-request split** in `_fetch_cells` (`src/cliproxy_usage_server/aggregate.py`): uncached input = input - cache read - cache creation; the four types are uncached input, cache read, cache creation, output. The SQL no longer reads the plan's `openai` flag (the `CostPlan.openai` field is removed) and no longer clamps cache reads to input. Whole-request plans compare `input_tokens` with the threshold; marginal plans tier each type's own amount, and a request counts as long-context when any of the four types exceeds the threshold.
6. **Pricing:** cache creation is priced at `Rates.cache_creation` under the same `CostPlan` rules; `cost_by_type` gains `cache_creation`.
7. **API** (`src/cliproxy_usage_server/schemas.py`, mirrored in `frontend/src/types/api.ts`): totals carry `input_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `output_tokens`, `reasoning_tokens`; series, trends and mix entries rename `cached_tokens` to `cache_read_tokens`; the CSV export carries all five. `cached_tokens`, `uncached_input_tokens` and `ModelPrice.cached_in_input` are removed.
8. **Frontend:** `tokens()` stays input + output, and every place showing tokens follows. Cache hit rate is cache read over input everywhere, model rows included. Drawer token tiles: Input (caption: share from cache reads), Output (caption: reasoning share), Cache writes (`cache_creation_tokens`; caption: share of input). Spend by token type has four parts (Input is the uncached part, Output, Cache read, Cache write); the cache savings line is unchanged.

9. **Version 0.3.0.** Bump `pyproject.toml` to `0.3.0`; `flake.nix` reads the version from `pyproject.toml` (`builtins.fromTOML`) instead of repeating it. `migration.py` ships in 0.3.x and is removed in 0.4.0, which its docstring states. Start `CHANGELOG.md` with a 0.3.0 entry (the changes above, the breaking schema change, and the upgrade steps: CLIProxyAPI v7.2.97+, the collector migrates on its first run and leaves the backup file, run a 0.3.x collector once before moving to 0.4+, the server refuses an unmigrated DB at startup, and a collector exits 2 on a DB from a newer version); `README.md` links to it. Tag `v0.3.0` on the merge commit.

Limitations, recorded in `AGENTS.md`: migrated Claude rows that wrote to the cache without reading it stay counted as cache reads, and Claude rows before v7.1.26 have no cache creation (their total did not include it).

## Constraints

- Only the migration function may know the old layout or classify rows by model name; every other read uses the new columns as defined above.
- Update `AGENTS.md`'s `user_version` description (`open_db`'s three cases, the migration's version gate, exit 2 for a newer DB, `run()`'s startup check) and its schema, token and pricing text (it describes `cached_tokens`, `price.cached_in_input`, the cached-in-input split and the positional `_INSERT` rule, which no longer applies), `docs/usage-scan-dedup.md`'s rollup schema and its token and clamp text (and its layout detection: the rollup becomes a version-1-to-2 step in the collector's `open_db` instead of comparing `sqlite_master` definitions; its server-startup rebuild and write are dropped in favor of item 4's check, and its tests become "a version-1 DB is rebuilt and set to 2" and "the server refuses a version-1 DB"), and `README.md`: its token, API and pricing notes (cached-excluded wording, the OpenAI subset note, the Anthropic cache-write undercount), the proxy requirement (CLIProxyAPI v7.2.97+), the backup file, and that the new server refuses an unmigrated DB at startup until the collector has run once (under a restarting supervisor it comes up after the next collector run).
