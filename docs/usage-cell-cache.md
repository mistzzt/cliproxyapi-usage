# Plan: serve usage from an in-process cell cache

## Goal

Every usage endpoint aggregates `_fetch_cells` (`src/cliproxy_usage_server/aggregate.py`): one grouped query over `requests` per window, plus the previous period, and `options` scans all history on every page. On the 1.5M-row snapshot (`test/cpa-usage.tar.gz`, migrated to schema version 1) an all-time page takes about 13 s, almost all of it in SQL. The server keeps per-cell token sums in memory and reads history from them, so pages take tens of milliseconds while the schema, the collector and the server's read-only access stay as they are.

Start from branch `proto/slot-cache-python` (commits `1ba3d77`, `6408714`): it implements this design, is exact, and was benchmarked at about 90 ms per all-time page and 20 MiB of memory. Merge it into this branch and trim it to the design below; delete `docs/proto-slot-cache-python.md` and `docs/usage-scan-dedup.md` (superseded by this plan; earlier plans that mention it stay as they are).

## Design

1. **Plan-independent grouped query.** One query groups `requests` into cells per (15-minute UTC slot, api_key, model, source). Per cell it sums the plain counts and every priced type's total, and for each plan shape `cost_plan` can produce (`pricing.PLAN_SHAPES`: marginal 200k, whole-request 200k, whole-request 272k) every type's base-rate share and the long-request count. Pricing picks each model's shape afterwards, so the query needs no plan join and no per-call `SELECT DISTINCT model`. The five priced types stay defined once (`_PRICED`).
2. **Cell cache.** One cache per server process holds every cell of the DB, keyed by slot and then by (api_key, model, source), with one shared copy of each distinct key string. `app.state.cell_cache` exposes `ready` and its `builds` and `hits` counters for tests and benchmarks. The app lifespan builds it with one scan in a background thread; until it is ready, requests use the direct query. Each cached read first folds in rows whose `rowid` is above the last seen maximum, under one lock. The cache is dropped and rebuilt in the background when the DB file is replaced (device and inode), `PRAGMA schema_version` changes, `MAX(rowid)` goes down, the row at the cached maximum `rowid` has a different timestamp (a reused rowid), or a `COUNT(*)` check, run at most every `USAGE_CELL_CACHE_VERIFY_SECONDS` (default 60), no longer equals the number of rows the cache has seen (evicted ones included). In-place `UPDATE`s of existing rows are not detected (the collector only appends), and `AGENTS.md` says so.
3. **Reads.** Whole slots inside a window come from the cache, filtered by raw key; the partial slots at each edge come from the grouped query bounded by the cached maximum `rowid`. Priced cells are memoized per slot for the current pricing map and dropped when a fold touches that slot. `resolve_filter` (distinct raw values per column) reads them from the cache after folding in new rows, instead of a `SELECT DISTINCT` over `requests` on every request; edge queries use the timestamp index whatever the filters (not the model, key or source indexes). The all-time axis start keeps its indexed SQL query, since cells keep no exact earliest timestamp.
4. **Memory cap.** `USAGE_CELL_CACHE_MAX_MB` (default 512) bounds the cache's estimated size: its cell count times a fixed bytes-per-cell constant covering a cell's sums plus one priced-memo entry. After a build or fold, the cache evicts its oldest slots until it fits and remembers the first slot it still holds; a build may exceed the cap until it finishes. Whole slots before that slot are read with the grouped query, bounded by the cached maximum `rowid` like the edges, and new rows landing there are not folded in but still count toward the rows the cache has seen. The group of rows whose timestamp SQLite cannot parse is never evicted. While anything is evicted, `resolve_filter` queries `requests`. Eviction is logged once with the setting's name.
5. **Switch.** `USAGE_CELL_CACHE=0` disables the cache; every request then uses the direct query.

Results stay exactly as today's code computes them, floats included: cells reach pricing in the same slot-then-key order with the same integer sums.

## Constraints

- The server stays read-only, the schema stays at version 1, and the collector does not change.

## Done when

- `uv run pytest`, `uv run ruff check`, `uv run ruff format --check` and `uv run basedpyright` pass. New tests on synthetic data compare cached and direct results (byte-identical JSON for summary, every breakdown dimension, options and export) for windows with mid-slot edges, each filter, rows inserted between requests, each rebuild trigger, a window inside one slot, a cap small enough to evict (windows before, across and after the first cached slot, plus options and filters), and requests during the build. A test measures real per-cell memory (e.g. with `tracemalloc`) with every slot's priced memo filled (cell sums plus memo entry), on cells with realistic-length keys, models and sources and token sums above 256, and fails if it exceeds the bytes-per-cell constant.
- `nix develop -c bash -c 'cd frontend && bun test && bun run lint && bun run build'` and the Playwright suite (command in `AGENTS.md`) pass.
- Measured with a scratch benchmark kept outside the repo (the handoff reports its path and the results table), on a copy of the migrated snapshot, each configuration in its own subprocess through `create_app` and `TestClient` (tz `America/Chicago`, fixed mid-slot end `2026-10-17T06:07:30Z` so every window has partial slots at both ends, pages of summary, person and model breakdowns and options), compared with `USAGE_CELL_CACHE=0` and with commit `2651e77`: byte-identical JSON for all time and 30 days (summary, both breakdowns, options); sequential pages at most 200 ms all time, 150 ms for 30 days unfiltered, with a model filter and with a credential filter, and 100 ms for 7 hours; cache ready within 5 s with no requests during the build; after inserting 10,000 rows through the collector's `insert_records` into that DB copy (cloned from existing rows, with timestamps after the snapshot's last row) and moving the page end past them, the next all-time page at most 250 ms, its summary's `requests` exactly 10,000 higher, and its JSON byte-identical to `USAGE_CELL_CACHE=0`; RSS after ready at most 60 MiB above the import-only RSS.
- `AGENTS.md` and `README.md` describe the cache, its knobs (`USAGE_CELL_CACHE`, `USAGE_CELL_CACHE_MAX_MB`, `USAGE_CELL_CACHE_VERIFY_SECONDS`), eviction and the startup warm-up.
